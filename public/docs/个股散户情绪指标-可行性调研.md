# 个股散户情绪指标 — 可行性调研报告

> 调研对象：基于东方财富股吧 24 小时帖子 + 大模型语义分析，产出个股散户情绪指标，在个股详情页新增子菜单。
>
> 调研方式：真实端点探测 + 真实数据取样 + 真实 LLM 调用验证（非纸面推演）。
>
> 调研日期：2026-10-18。所有结论均有实测数据支撑，未经验证的部分已显式标注。

---

## 一、执行摘要

**结论：技术可行，但可行性受「抓取层」而非「分析层」严格约束，需按降级方案实施。**

三个层面分别判定：

| 层面 | 判定 | 依据 |
|---|---|---|
| 数据源可得性 | **可用，但无反爬豁免** | 列表页 SSR 内嵌完整 JSON，字段齐全；但实测触发「身份核实」封锁，持续 9 分钟以上未恢复 |
| 语义分析质量 | **可用，质量超出预期** | 真实 24h 帖子跑通 LLM，能自动区分资讯贴与散户自发发言，主动降级置信度 |
| 工程落地成本 | **低（LLM 侧）/ 中高（抓取侧）** | 单股单日 LLM 成本可忽略；抓取请求配额才是真正的瓶颈 |

**核心矛盾**：大模型侧几乎零成本、零风险，而东方财富的反爬机制是唯一的、也是决定性的瓶颈。方案设计的全部重点应放在「如何用最少的请求拿到足够的信息」，而不是「如何让模型分析得更准」。

**推荐的降级方案**：只抓股吧列表页标题（每只股票 1 个请求 / 天），放弃逐帖正文抓取。理由是实测证明标题已能支撑情绪判断，而正文抓取会使请求量放大 8 倍，直接触及反爬红线。

## 二、数据源实测

### 2.1 端点真伪甄别（重要）

调研初期检索到的多处「股吧接口」均为**虚构或不适用**，逐一实测结果如下：

| 候选端点 | 实测结果 | 判定 |
|---|---|---|
| `guba.eastmoney.com/api/Get?code=` | HTTP 404 `Not Found` | 不存在 |
| `gbapi.eastmoney.com/webarticlelist` | HTTP 403（空 body） | 需未知签名参数，不可用 |
| `gbapi.eastmoney.com/list` | HTTP 403 | 不可用 |
| `gbpush.eastmoney.com/api/post/list` | HTTP 200 但返回东方财富 WAP 首页 | 端点不存在，被兜底重定向 |
| `emappdata.eastmoney.com/stockrank/*`（GET） | `{"status":-1,"message":"服务异常"}` | 需 POST + 特定 body |
| **`guba.eastmoney.com/list,{code}.html`** | **HTTP 200，SSR 内嵌 `var article_list` 完整 JSON** | **唯一可用主数据源** |
| **`guba.eastmoney.com/news,{code},{post_id}.html`** | **HTTP 200，JSON 内含 `post_content` 正文** | **正文数据源** |
| **`emappdata.eastmoney.com/stockrank/getAllCurrentList`（POST）** | **HTTP 200，返回全市场人气排名** | **热度维度补充源** |

教训：网络上流传的股吧接口大量为二手转述或模型臆造，**必须逐条实测后再纳入设计**。

### 2.2 主数据源：列表页 SSR JSON

列表页 HTML 约 167 KB，其中内嵌 `var article_list = {...}`（约 119 KB），是完整结构化数据，无需解析 DOM。

顶层结构：

```
{ "re": [...帖子数组...], "count": 977652, "bar_name": "贵州茅台",
  "bar_code": "600519", "bar_quot_code": "SH600519", "bar_info": {...},
  "rc": 1, "me": "操作成功", "time": "2026-10-18T14:40:16+08:00" }
```

单条帖子可用字段（实测完整列表）：

| 字段 | 示例 | 价值 |
|---|---|---|
| `post_id` | 1783881855 | 唯一键，去重必需 |
| `post_title` | 白酒"取悦"年轻人… | **核心分析输入** |
| `post_publish_time` | 2026-10-17 21:52:51 | 时间窗口筛选 |
| `post_display_time` | 2026-10-17 21:35:15 | 与上者略有差异，取 publish |
| `post_click_count` | 3541 | 互动量，用于加权/采样 |
| `post_comment_count` | 27 | 互动量 |
| `post_forward_count` | 4 | 互动量 |
| `user_id` / `user_nickname` | 7344113638256342 / 贵州茅台资讯 | 识别资讯号 / 水军 |
| `stockbar_code` | 600519 | **必须校验，列表会混入跨吧推荐内容** |
| `post_top_status` | 1 = 置顶 | 置顶帖不代表当期情绪，需剔除或降权 |
| `post_has_pic` / `post_has_video` | bool | 纯图帖标题常无意义 |
| `bullish_bearish` | 恒为 0 | 东财未提供官方情绪标注，字段不可用 |
| `user_is_majia` | True | 疑似小号标记，可用于降权 |

**关键校验**：列表页会混入非目标股吧的推荐内容（实测抓茅台时出现「财富号评论」bar 的帖子）。**必须按 `stockbar_code == 目标代码` 过滤**，否则情绪样本被污染。

### 2.3 正文数据源

详情页 HTML 中无独立正文 DOM，正文位于内嵌 JSON 的 `post_content` 字段，值为 HTML 片段：

```
"post_content":"<div class=\"xeditor_content cfh_web\"><p>今天盘面把人打懵了。沪指跌1.59%…</p><div class=\"wrap-img\"><img src=\"...\"/></div>…"
```

需做 HTML 清洗（去标签、`&nbsp;`、图片占位符）。正文长度通常 200–2000 字，信息量显著高于标题。

**但正文必须逐帖单独请求**（无批量接口），这是它最大的工程代价。

### 2.4 热度维度补充源

`POST https://emappdata.eastmoney.com/stockrank/getAllCurrentList`

```json
{"appId":"appId01","globalId":"786e4c21-70dc-435a-93bb-38f21a2b3a1e",
 "marketType":"","pageNo":1,"pageSize":20}
```

返回 `{"sc":"SH600519","rk":9,"rc":0,"hisRc":-2}`，即「代码 / 当前排名 / 排名变化」。**一次请求可取全市场排名**，成本极低，是比股吧帖子数更干净的「关注度」度量。

局限：仅反映全市场相对排名（Top N 之外无数据），且未验证是否提供历史序列。建议只作为辅助热度因子，不作为主指标。

## 三、反爬机制实测（本报告最关键部分）

### 3.1 触发与表现

调研过程中累计发出约 **80–100 个请求 / 约 10 分钟**（含多次连续请求、无随机间隔），随后触发封锁：

| 观测项 | 结果 |
|---|---|
| HTTP 状态码 | **200**（不是 403，具有强欺骗性） |
| 响应体大小 | 2826 字节（正常 167000 字节） |
| 页面文本 | **「身份核实」** |
| 影响范围 | **IP 级、全站**：列表页、详情页、首页全部被拦 |
| Cookie | 不下发任何 cookie，`Set-Cookie` 为空 |
| 恢复时间 | **≥9 分钟未恢复**（截至调研结束仍处封锁态） |
| 换 User-Agent | 无效 |
| 换 Session + 完整浏览器头 | 无效 |

### 3.2 对工程实现的硬性要求

1. **绝不能用 HTTP 状态码判断成功**。必须校验响应体是否包含 `var article_list`（列表页）或 `post_content`（详情页），长度 `< 10000` 字节可直接判为被拦。这一点如果做错，会把「身份核实」页当成正常数据解析，导致静默产出空结果——比直接报错更危险。
2. **必须实现退避**。一旦命中验证页，应立即停止该 IP 的全部请求并进入冷却（建议 ≥30 分钟），继续重试只会延长封锁。
3. **请求速率必须远低于触发阈值**。实测阈值约 600 请求/小时量级。生产建议控制在 **≤60 请求/小时/单 IP**，即每 60 秒 1 个请求，留 10 倍安全边际。
4. **需要代理池或分布式出口**（若监控池规模超过下述估算上限）。

### 3.3 请求预算推算

按「只抓列表页标题」的方案：

| 监控池规模 | 每只请求数 | 日总请求 | 按 60 请求/小时所需时长 | 可行性 |
|---|---|---|---|---|
| 50 只 | 1–3（翻页） | 50–150 | 1–2.5 小时 | 可行，单 IP 足够 |
| 200 只 | 1–3 | 200–600 | 3–10 小时 | 可行但紧张，需分散到全天 |
| 500 只 | 1–3 | 500–1500 | 8–25 小时 | 单 IP 临界，建议代理或缩减池 |
| 500 只 + 正文 | 11（3 页 + 8 正文） | 5500 | 90+ 小时 | **单 IP 不可行** |

结论：**如果沿用项目现有「监控池 = 500 只」的规模，正文抓取方案在单 IP 下不成立**，只能走标题方案；若必须做正文，必须引入代理池或把分析范围收窄到核心持仓/自选。

## 四、数据质量与样本量实测

### 4.1 交易日 vs 周末的帖子量差异（10 倍量级）

实测抓取三只不同热度股票的全量历史（去重后 813 / 955 / 1051 条），按日统计：

| 股票 | 10-17 周六 | 10-18 周日 | 10-16 周五 | 10-15 周四 | 10-14 周三 | 10-13 周二 |
|---|---|---|---|---|---|---|
| 贵州茅台 600519（超热） | 30 | 20 | 168 | **324** | 122 | 126 |
| 平安银行 000001（中热） | 3 | 1 | 33 | 45 | 57 | 43 |
| 读者传媒 603999（冷门） | 12 | 5 | 115 | 70 | 46 | 18 |

关键结论：

1. **交易日单股日均 30–170 条**（热门股单日可破 300，小盘股被炒作时也会突然爆量）。
2. **周末骤降 85% 以上**（茅台 324 → 20）。若按 24h 滚动窗口，**周一早上的样本会混入大量周末低活跃内容**，需在指标上标注「低活跃」状态。
3. **冷门股存在零样本日**。实测「名臣健康 002919」24 小时内 **0 条帖子**。这类股票无法产出情绪值，必须设计明确的「无数据」态，不能用 0 或 50 填充（会产生虚假信号）。

### 4.2 资讯贴占比

按作者昵称含「资讯 / 财经 / 证券」统计：

- 交易日：**3.6%–4.9%**
- 周末：**20%**（散户不发帖时，资讯号占比被动升高）

但需注意：POC 中模型判断「茅台 29 条中超半数为资讯转贴」，说明**散户自己转发的资讯内容**也大量存在，按账号名统计会严重低估。这类内容对情绪判断无价值，必须在 prompt 中显式要求模型区分并剔除。

### 4.3 互动量分布（用于采样加权）

茅台 24h 样本：点击数中位数 198 / 最大 8269；评论数中位数 1 / 最大 29。

分布极度右偏——少数帖子占据绝大部分关注。这支持「**按互动量加权的分层采样**」而非简单截断：高互动帖代表群体关注焦点，低互动帖代表长尾声量，两者都要有代表。

### 4.4 关键限制：历史深度不足

实测列表页**翻页深度有限**（`f_10` 及以后在未触发封锁时也可能无数据），单只股票可回溯的历史约 **8–10 天**（热门股更快见底，冷门股可回溯 70+ 天）。

这意味着：

- **趋势图初期只能画 8–10 天**，不足以形成有价值的情绪曲线。
- **无法用历史数据回测指标有效性**。这是最严重的后果——情绪指标若不能证明与未来收益有相关性，产品价值就无法成立。
- 唯一出路：**从功能上线日起每日落库，自行积累时间序列**。3 个月后才有 60+ 个数据点，6 个月后才具备初步回测条件。

> 这一点应在产品决策阶段就对齐预期：**该功能的价值是「上线后逐步积累出来的」，不是「上线即有」**。

## 五、大模型语义分析验证（POC）

### 5.1 验证设置

取真实 24 小时帖子（茅台 29 条 / 平安银行 4 条），按互动量取前 8 条抓取正文摘要，构造单次 prompt，调用项目现有 LLM 场景同款模型 `doubao-seed-2-0-mini-260428`，要求输出严格 JSON。

### 5.2 实测输出

**贵州茅台（29 条样本）**：

```json
{"sentiment_score": 58, "bullish_ratio": 27, "neutral_ratio": 60, "bearish_ratio": 13,
 "heat_level": "冷清", "confidence": 35,
 "dominant_topic": "散户围绕贵州茅台的股价走势、投资动作及行业相关内容展开零散讨论",
 "reasoning": "本次样本含29条帖，其中超半数为资讯转贴不计入散户情绪，有效自发帖仅11条。有效帖中少数看多（如1300满仓、年底上1500），少量看空（如茅台对经济无用），多数中性闲聊，缺乏统一情绪，样本少可信度低。",
 "keywords": ["贵州茅台","满仓","股价","筹码峰"],
 "notable_posts": [{"title":"1300满仓了，下周一突破？真香啊","stance":"看多"},
                   {"title":"这种企业对物质和经济的发展没一点作用…","stance":"看空"}]}
```

**平安银行（4 条样本）**：`sentiment_score 45 / confidence 65`，识别出「梭哈」「托」「清仓」等散户黑话，并逐条给出立场标注。

### 5.3 验证结论

| 验证项 | 结果 |
|---|---|
| 严格 JSON 输出 | **稳定**，两次调用均无需修复即可 `json.loads` |
| 资讯贴识别 | **主动识别并说明如何加权**，未被动计入情绪 |
| 样本不足自我降级 | **做到了**（29 条 → confidence 35，并说明原因） |
| 散户黑话理解 | **准确**（梭哈 / 满仓 / 割肉 / 托 / 上车） |
| 内部逻辑自洽 | **成立**：0.27×100 + 0.60×50 + 0.13×0 = 57 ≈ 58 |
| 响应耗时 | 3.7s / 5.3s |
| Token 消耗 | 输入 2808 + 输出 264（29 条样本）；输入 913 + 输出 286（4 条样本） |

**唯一缺陷**：平安银行仅 4 条样本时给了 confidence 65，偏乐观。需要在 prompt 中对 confidence 的标定做更硬的约束（例如按样本量分档封顶）。

### 5.4 一个重要的设计建议

POC 显示 `sentiment_score` 与三项占比严格自洽。建议**不让模型直接给 0–100 总分**，而是：

1. 模型只输出 `bullish/neutral/bearish` 三分类占比 + 理由 + 置信度；
2. **情绪分由后端固定公式计算**：`score = 0.5 + (bullish% − bearish%) / 200`，映射到 0–100。

好处：可复现、可解释、不受模型漂移影响，且换模型时历史序列不会断裂。模型的判断力用在「理解文本」上，算术交给代码。

## 六、指标体系设计建议

### 6.1 主指标

| 指标 | 定义 | 用途 |
|---|---|---|
| `sentiment_score` | 0–100，50 为中性，由三分类占比公式计算 | 主曲线 |
| `confidence` | 0–100，样本量与信号强度 | **必须与主指标同时展示**，低置信度时视觉降级 |
| `heat_level` | 冷清 / 正常 / 活跃 / 过热 | 判断情绪是否有代表性 |
| `post_count` | 24h 帖子数 | 热度原始值 |

### 6.2 与现有「恐惧贪婪」的关系（必须明确区分）

项目已有 `stocks_fear_greed` 表，是**基于 OHLCV 技术指标计算**的价量情绪，与本指标语义完全不同：

| | 恐惧贪婪（现有） | 散户情绪（新增） |
|---|---|---|
| 数据来源 | 价量技术指标（波动率/动量/成交量） | 股吧文本语义 |
| 反映 | 价格行为隐含的情绪 | 散户**主观表达**的情绪 |
| 更新 | 收盘后计算 | 可盘中滚动 |
| 表 | `stocks_fear_greed` | **必须独立建表** |

**绝不可写入 `stocks_fear_greed`**：该表是 `(trade_date, index_code)` 复合主键，混写会覆盖个股恐贪历史。

### 6.3 该指标真正的产品价值（设计取向建议）

散户情绪的价值**不在绝对水平，而在两个地方**：

1. **极端值**：极度看多（>85）往往对应顶部区域，极度看空（<15）对应恐慌底部——它是**反向指标**。
2. **背离**：股价新高但情绪分持续走低（散户在派发），或股价新低但情绪分回升（散户在承接）。这是最有交易价值的信号。

因此前端不应只画一条情绪线，而应提供：

- 情绪分 + 收盘价**双轴叠加图**（直接看背离），复用现有恐惧贪婪卡片的双轴写法；
- 情绪 5 日 / 20 日变化率；
- 明确的「情绪—价格背离」状态标记。

若只给一个孤立的分数字，交易价值接近于零。

## 七、工程落点与成本

### 7.1 落点（已核对现有代码）

| 层 | 位置 | 说明 |
|---|---|---|
| 前端入口 | `../../src/views/stock/StockDetail.vue` 的 `tabItems`（第 447–454 行） | 新增第 7 个 Tab「散户情绪」 |
| 前端图表 | 同文件第 94–183 行双轴写法、`../../src/utils/echartsTheme.js` | 直接复用主题 |
| 后端路由 | `../../routes/stock.py`（照第 731 行 `greed_data` 模式） | `GET /api/v1/stock/retail_sentiment/{symbol}` |
| 新表 | `../../models/__init__.py` | `stock_guba_sentiment`，唯一键 `(symbol, trade_date)` |
| 调度 | `../../scheduler_jobs.yaml` | 避开 18:50/18:55 的恐贪任务 |
| LLM 场景 | `../../config.py` + `llms/llm_setting.py::LLM_SETTING_SCENES` | 新增 `stock_retail_sentiment`，两处必须同步 |

已知约束（沿用项目既有经验）：

- `job/job_server.py::_job_registry` 必须登记新 job，否则消息被静默 ACK 丢弃；

- 新表必须 `(symbol, trade_date)` 复合主键或唯一约束（`StockFearGreed` 曾因单列主键导致同一天多票被 ORM 静默去重）。

### 7.2 成本测算

**LLM 成本（可忽略）**：

按 100 条标题 / 次、单股单日 1 次调用估算，约 3000–4000 输入 tokens + 300 输出 tokens。

| 监控池 | 日 tokens | 月成本量级（按 mini 级模型公开价） |
|---|---|---|
| 50 只 | 约 20 万 | 个位数人民币 |
| 200 只 | 约 80 万 | 十元级 |
| 500 只 | 约 200 万 | 数十元级 |

> 价格请以实际账单为准；项目 `llm_token_usage` 表只统计 token，无金额字段，若需成本看板要自行维护单价配置。

**抓取成本（真正的约束）**：见 3.3 节。瓶颈是请求配额，不是算力或钱。

**存储成本（可忽略）**：只存日聚合，500 只 × 250 交易日 = 12.5 万行/年，远小于现有因子表。

### 7.3 落库策略建议

只存**日聚合**，不存帖子明细（或仅保留 7 天用于 debug）。理由：帖子明细留存既无查询场景，又要面对合规与存储压力。

## 八、风险矩阵

| # | 风险 | 概率 | 影响 | 对策 |
|---|---|---|---|---|
| 1 | **反爬封锁导致采集中断** | 高 | 高 | 严格限速（≤60 请求/小时）+ 校验响应体 + 退避冷却 + 可选代理池；失败降级为「沿用上一日 + 标记 stale」 |
| 2 | **历史深度不足，无法回测** | 确定 | 高 | 上线即开始积累；前期只展示「数据积累中」，不展示趋势结论 |
| 3 | **指标无预测力（伪信号）** | 中 | 高 | 积累 60+ 交易日后做相关性检验；不通过则终止该功能 |
| 4 | 页面结构改版 | 中 | 中 | 解析层独立封装 + 每日校验字段完整性，异常即告警 |
| 5 | 冷门股零样本 | 确定 | 低 | 明确「样本不足」态，不填充默认值 |
| 6 | 水军 / 机器人刷帖污染 | 中 | 中 | 用 `user_is_majia`、单账号发帖频次、`post_click_count` 异常值降权 |
| 7 | 合规（股吧服务条款） | 中 | 中 | 控制频率、不存储用户身份信息、不对外分发原文；建议做成可开关配置 |
| 8 | 周末/假期样本失真 | 确定 | 低 | 标注低活跃状态，周末不做趋势判断 |

**风险 1 与 3 是决定功能成败的两个关口**：前者决定「能不能持续拿到数据」，后者决定「拿到数据后是否有用」。二者都必须在正式开发前或开发早期验证。

## 九、分阶段实施建议

**Phase 0：有效性预验证（建议先做，1–2 天）**

不写业务代码，只做一件事：用极低频抓取，对 10–20 只股票积累 20 个交易日的情绪分，然后检验「情绪分」与「未来 1/3/5 日收益」的相关性，以及「极端情绪 → 反转」的胜率。

- 若相关性显著 → 进入 Phase 1。
- 若无相关性 → 止损，不投入 UI 与工程开发。

> 这一步的成本极低（不过是一次性脚本 + 20 天等待或近似回溯），但能避免在无效指标上投入完整开发周期。

**Phase 1：数据管道 + 标题级情绪（最小可用）**

- 抓取器（严格限速、响应体校验、退避、单 IP 冷却）
- 标题级 LLM 分析 + 后端公式算分
- 日聚合落库 + 调度
- 只覆盖核心监控池（建议 50–100 只）

**Phase 2：前端子菜单**

- 新增 Tab：当前读数 + 置信度 + 多空占比 + 情绪/价格双轴图 + 背离标记
- 明确「数据积累中」态

**Phase 3：增强（视 Phase 0/1 结果决定）**

- 关键标的高互动帖正文抓取（请求量允许时）
- 人气榜热度因子
- 主题词云 / 代表性帖子摘要
- 代理池扩容

## 十、待决策问题

以下问题需要产品侧确认，会显著影响实现方案：

1. **分析范围**：全监控池（500 只，单 IP 不可行，需代理）还是核心池（50–100 只，单 IP 可行）？
2. **是否接受「只用标题、不抓正文」**？这会损失部分语义细节，但请求量降为 1/11，是单 IP 可持续的前提。
3. **是否接受「前期只有 8–10 天历史，趋势靠日后积累」**？若不接受，则需要另寻能提供长历史的数据源（目前未找到）。
4. **采集时点**：固定在收盘后 15:30 采集过去 24h（口径稳定，便于跨日比较），还是全天滚动更新？
5. **运维假设**：生产环境是否有可用代理？若无，Phase 3 的正文抓取基本不成立。
